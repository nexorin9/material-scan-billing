# 主数据导入与热更新口径

> 耗材主数据与手术排台**天天在变**：新耗材建档、耗材停用、临时加台、提前关台。
> 这张纸讲清三件事：**主数据从哪来、变了多久生效、现在用的是哪一版**。

## 一句话口径

**导入即生效 · 不重启不中断**：主数据一导入，判定立刻按新值走 —— 正在跑的守护进程**不用重启**，
下一次扫码就用新值判。停用耗材当场不再绑定，关台当场拒绑并转人工。

## 主数据从哪来（权威来源）

| 主数据 | 院内权威 | 本地镜像表 | 主键 |
|--------|----------|------------|------|
| 手术排台台次 | 手术排台 | `operation` | `operation_no` |
| 院内耗材主数据 | 耗材主数据（高值耗材管理岗维护） | `material` | `material_code` |

本进程**只读**镜像表，不回写院内主数据；主数据的变更由院内权威侧导出 CSV，
再导入本进程。

## 怎么导入（两条路，同一条导入逻辑）

### ① 运维命令导一次（人工触发）

```bash
node dist/cli.js import-master \
  --operations /path/to/operations.csv \
  --materials  /path/to/materials.csv
```

输出示例：

```
== 主数据导入 ==
  主数据版本：第 2 版　导入时间 2026-11-03T10:12:31+08:00　来源 cli
  排台台次：文件 2 行　新增 0　更新 2　跳过 0　镜像行数 2 → 2
  耗材主数据：文件 6 行　新增 1　更新 5　跳过 0　镜像行数 5 → 6
  导入即生效：正在跑的守护进程无需重启，下一次扫码按新值判定
```

### ② 守护进程自动热更新（无人值守）

配两个环境变量即可（见 `.env.example`）：

```bash
MASTER_DATA_OPERATIONS_CSV=/var/spool/.../master-data/operations.csv
MASTER_DATA_MATERIALS_CSV=/var/spool/.../master-data/materials.csv
MASTER_DATA_RELOAD_INTERVAL_MS=30000     # 默认 30 秒
```

守护进程按「**修改时间 + 文件大小**」给文件取指纹（不读全文、不猜内容）：
文件变了就重导一次，版本号 +1，导入履历与审计链各留一行。

## CSV 字段要求

### 排台台次 `operations.csv`

| 字段 | 必填 | 说明 |
|------|------|------|
| `operation_no` | 是 | 台次号（主键） |
| `room_no` | 是 | 手术间号 |
| `dept_code` | 是 | 科室编码 |
| `status` | 是 | `open` / `closed`（关台即时生效） |
| `closed_at` | 否 | 关台时间（`status=closed` 时建议填） |

### 耗材主数据 `materials.csv`

| 字段 | 必填 | 说明 |
|------|------|------|
| `material_code` | 是 | 耗材码（主键，归一后的规范码） |
| `name` | 是 | 耗材名称 |
| `price_code` | 是 | 价码（计费回写用） |
| `fee_category` | 是 | 费用类别（院内 14 类口径，见 `docs/api/fee-category.md`） |
| `medical_insurance_class` | 是 | 医保分类（甲类 / 乙类 / 丙类） |
| `active` | 否 | 启用状态；`false` = **停用（失效标记，不删行）**，留空按启用处理 |
| `batch_no` | 否 | 批号（v2 幂等档位参与去重） |
| `unit_pack` / `unit_min` / `charge_unit` / `ratio` | 否 | 包装 / 最小 / 计价单位与换算系数（见 `docs/api/units.md`） |

**坏行不拖垮整份文件**：缺字段、状态非法、启用状态非法的行会被跳过，
其余行照常导入；每条跳过都带**原始行号 + 中文原因**，进导入履历、运行摘要与 doctor 输出。

## 失效怎么表达（不物理删除）

| 业务变化 | 怎么表达 | 判定立刻怎么变 |
|----------|----------|----------------|
| 耗材停用 | `active=false` | 判 `NOT_REGISTERED` / `MATERIAL_INACTIVE`，升核查条目，**不落台账不计费** |
| 台次关台 | `status=closed` | 判 `CLOSED` / `OPERATION_CLOSED`，升核查条目，**不自动补录** |
| 耗材改价码 | 改 `price_code` | 下一次绑定的台账行直接落新价码 |
| 新耗材建档 | 加一行 | 原来判「未建档」的耗材码当场可绑 |

历史行一律保留（`operation` / `material` / `material_binding` 都不删）——
「上个月用了哪支耗材」要能对账，删了就说不清了。

## 版本号（现在用的是哪一版主数据）

- **每次成功导入版本号 +1**；导入中途失败 → 事务回滚 → **版本号不前移**（仍在用上一版）。
- 版本号、导入前后行数、逐条跳过原因都落在 `master_data_import` 表（只增不改）。
- 每次导入在**只增不改的审计链**里留一行 `master_data_imported`（含版本号与影响行数），
  哈希链完整性照常可校验。

查当前版本：

```bash
node dist/cli.js doctor        # 「== 主数据 ==」段：当前版本、最近导入时间、逐次导入前后行数
node dist/cli.js summary       # 运行摘要里同样有主数据版本与跳过条数
```

## 失败怎么表现

| 场景 | 表现 | 结果 |
|------|------|------|
| 某一行有坏字段 | 该行跳过，原因进履历 | 其余行照常导入，**版本号照常递增** |
| 整个导入失败（磁盘满 / 库被占用） | 错误码 `ERR_MASTER_DATA_IMPORT_FAILED` | 事务回滚，**版本号不前移**，判定仍按上一版主数据走 |
| 热更新时文件读不到（网关正在写） | 错误码 `ERR_MASTER_DATA_IMPORT_FAILED` | 本轮不导、**不删已有主数据**，下轮重试 |

处置口径见 `docs/api/errors.md`。

## 与判定引擎的关系

判定引擎（`src/engine/`）**每次现读**镜像表，**不缓存主数据快照**：

```
扫码事件 → 三层校验（查当前 material 表）→ 台次状态（查当前 operation 表）
        → 五种结论归类 → 落台账 / 升核查条目
```

所以「导入即生效」不是靠刷新缓存做到的，而是**判定路径本来就不缓存**——
热更新只要把新值写进镜像表，下一次判定自然就是新值。
