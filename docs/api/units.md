# 数量与计价单位换算（包装数 → 计价单位数）

> 扫码枪扫一次记的是**包装数**（扫到一个「包」记 1），HIS 计费要的是**计价单位数**
> （这个包里有 5 支就记 5 支）。换算错一个数量就是一次错账 ——
> 多算一倍是浪费耗材，少算一半是科室自己贴钱。

这份文档说清四件事：口径三列与换算系数怎么填、换算的判定规则、
算不出来时怎么处置、以及怎么把主数据的问题在**导入时**就揪出来。

## 一、主数据四列

| 列 | 含义 | 例子 |
|----|------|------|
| `unit_pack` | 扫码计数单位（设备扫的那个包装单位） | `包` |
| `unit_min` | 最小单位（拆零后的最小可计数单位） | `支` |
| `charge_unit` | 计价单位（HIS 按什么单位收钱） | `支` |
| `ratio` | 换算系数：**1 个扫码计数单位 = ratio 个计价单位** | `5` |

三列单位名 + 一个系数，就是耗材管理岗要维护的全部内容。

`ratio` 的两个方向：

- 系数 **> 1**（包比支粗）：`1 包 = 5 支` → `ratio = 5`，扫码 2 包 → 计费 10 支；
- 系数 **< 1**（计价单位比扫码单位粗）：`2 支 = 1 套` → `ratio = 0.5`，扫码 4 支 → 计费 2 套。

## 二、换算的判定规则

判定顺序逐层短路，**先给最具体的原因码**：

| 顺序 | 条件 | 原因码 | 错误码 | 处置 |
|------|------|--------|--------|------|
| ① | 数量不是正数（零 / 负数 / 非数值） | `UNIT_QUANTITY_NOT_POSITIVE` | `ERR_UNIT_QUANTITY_NOT_POSITIVE` | 核对扫码枪上报的数量；多半是设备录入问题，改正后重扫 |
| ② | 三个单位名缺一 | `UNIT_UNIT_MISSING` | `ERR_UNIT_UNIT_MISSING` | 由耗材管理岗补齐 `unit_pack` / `unit_min` / `charge_unit` 后重新导入 |
| ③ | `ratio` 未登记（含写成「五支一包」这类中文） | `UNIT_RATIO_MISSING` | `ERR_UNIT_RATIO_MISSING` | 补录 `ratio` 列后重新导入；补录前该耗材只进核查清单，不计费 |
| ④ | `ratio` 不是正数（0 或负数） | `UNIT_RATIO_INVALID` | `ERR_UNIT_RATIO_INVALID` | 核对 `ratio` 列；系统不会替它取整或补默认值 |
| ⑤ | 三个单位名与 `ratio` 对不上 | `UNIT_MAPPING_INCONSISTENT` | `ERR_UNIT_MAPPING_INCONSISTENT` | 核对单位三列与系数是否对得上；补齐后再导入，系统不猜口径 |
| ⑥ | 换算结果不是整数（除不尽） | `QUANTITY_NOT_DIVISIBLE` | `ERR_QUANTITY_NOT_DIVISIBLE` | 核对包装与计价单位的换算关系；**不四舍五入、不静默取整**，转人工 |

第 ⑤ 条的自洽口径（三选一）：

- `ratio = 1` → 计价单位只能是**扫码计数单位**或**最小单位**（两者指同一物）；
- 计价单位 = 扫码计数单位 → `ratio` **必须**是 1（按包装计价就按包装数计）；
- 计价单位 = 最小单位 → `ratio` **不能小于 1**（一个包装最少含一个最小单位）。

### 不四舍五入、不静默取整

`3 支` 按 `2 支 = 1 包`（`ratio = 0.5`）换算得 `1.5 包` —— **除不尽**。
这时系统**不做**四舍五入、不做取整，直接判异常转人工：要么包装规格录错了，
要么这次上报的数量不对。宁可让人来看一眼，也不要悄悄算错账。

## 三、换算轨迹（落台账，事后可核对）

台账行（`material_binding`）多两列：

| 列 | 内容 |
|----|------|
| `quantity` | 原始数量（**扫码计数单位**的个数，设备上报的那个数） |
| `charge_quantity` | 计价数量（**换算结果**；异常时为 null） |
| `quantity_trace` | 换算轨迹 JSON：原始数量 / 包装单位 / 系数 / 计价数量 / 计价单位 |

轨迹四要素（`material_code` / `raw_quantity` / `pack_unit` / `ratio` / `charge_unit` /
`charge_quantity`）**成功与失败都落** —— 失败时 `charge_quantity` 为 null，
事后能看到「当时算的是什么、为什么没算出来」。

计费回写用的是 **`charge_quantity`**，原始包装数不进载荷；
首次提交与退避重投**用同一个数**（见 `src/charge/quantity.ts`），
不会出现「第一次报 5 支、重投报 1 包」这种错账。

## 四、主数据的问题在导入时就暴露

耗材管理岗维护的 `ratio` 列，漏录、录成 0、写成中文都很常见。
本系统的口径是：**问题在导入时暴露，不留到运行期才炸**。

- 导入器逐行做单位口径自洽性检查；
- **问题行照常导入**（主数据是院内权威，导入器不替耗材管理岗删行），
  同时在**待补录清单**（`master_data_gap` 表）登记一条；
- 补录后重新导入且口径已自洽 → 该耗材的待补录条目**自动销项**
  （耗材管理岗可能改完又改坏，清单如实反映当前状态）。

待补录清单在 `doctor` 子命令里能直接看到：

```bash
node dist/cli.js doctor --db data/ledger.db
```

```
== 耗材主数据待补录（单位口径） ==
  待补录 2 条，已销项 1 条
  MAT-UNIT-PACK5             UNIT_RATIO_MISSING            耗材单位口径缺换算系数：1 个包折算成多少个支未登记
  MAT-UNIT-BAD               UNIT_MAPPING_INCONSISTENT     耗材单位口径不自洽：按最小单位（支）计价时，换算系数不能小于 1，当前为 0.5
  补录主数据后重新导入即自动销项；口径见 docs/api/units.md
```

**待补录清单**与**核查任务台账**是两件事：

- 核查任务（`check_task`）是**某一台手术的某一条耗材**卡住了；
- 待补录清单（`master_data_gap`）是**某一条耗材主数据**本身缺登记 ——
  补好了，那一类扫码会自己好起来，不用逐台手术去人工核。

## 五、升级前的老账怎么办

台账迁移的 **v14 版**（`unit_conversion`）会：

1. 给耗材主数据补 `unit_pack` / `unit_min` / `charge_unit` / `ratio` 四列，
   存量行按 **1:1** 补齐（包装即计价），**不改变升级前的计费行为**；
2. 给台账行补 `charge_quantity` / `quantity_trace` 两列；
3. 建 `master_data_gap` 待补录清单表。

1:1 补齐是**假定值**，所以每条存量耗材都会登记一条 `UNIT_RATIO_ASSUMED` 待补录 ——
耗材管理岗按真实包装规格补录 `ratio` 后重新导入，条目自动销项。
