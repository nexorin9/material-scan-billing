# 企业微信批次摘要推送对接规范

> 出站推送路径：每批扫码结算完成后，把**本批结论摘要**推到**既有**企业微信群（不新造消息中心）。
> 常驻守护进程默认走**按台次聚合节流**（同一台次的异常合并成一条消息，见 §8.5）。
> 本文件是**对端联调的唯一依据**：字段名与错误码逐字对齐实现代码（`src/check/notify.ts`、`src/check/message-template.ts`）。

## 1. 端点与方法

| 项 | 值 |
|---|---|
| 协议 | HTTP/1.1 + JSON（`application/json; charset=utf-8`） |
| 方法 | `POST` |
| 完整 URL | `{WECOM_WEBHOOK_URL}`（院内配发的企业微信群机器人地址，**自带 `key` 查询参数**） |
| 方向 | **写**（本系统 → 企业微信群机器人） |
| 请求超时 | 默认 5000 毫秒 |
| 凭据来源 | `WECOM_WEBHOOK_URL`（地址含 `key`）、`WECOM_SECRET`（加签密钥）；**一律取自环境变量** |

## 2. 加签（签名）

企业微信群机器人开启「加签」后，webhook 地址需带 `timestamp` 与 `sign` 两个查询参数：

```
sign = sha1("{timestamp}{secret}{key}")
```

| 项 | 取值 |
|---|---|
| `timestamp` | unix 秒（由本系统取当前时间） |
| `secret` | `WECOM_SECRET`（加签密钥，**不出现在请求体与日志里**） |
| `key` | webhook 地址上 `key` 查询参数的**值**（机器人凭据） |
| `sign` | 上述字符串的 SHA1 十六进制小写值 |

最终地址形如：

```
https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<KEY>&timestamp=<TS>&sign=<SIGN>
```

> **凭据单一出口**：`key` 与 `secret` 只在推送层读取。业务层拿得到「能发消息的客户端」，
> 拿不到凭据字符串；日志里的端点一律去掉 query（打码为 `?***`）。

## 3. 请求头

| 请求头 | 值 | 说明 |
|---|---|---|
| `content-type` | `application/json; charset=utf-8` | 固定 |
| `accept` | `application/json` | 固定 |

## 4. 请求体字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `msgtype` | string | 是 | 固定 `markdown` |
| `markdown` | object | 是 | markdown 消息体 |
| `markdown.content` | string | 是 | 批次摘要正文（见 §5） |

示例请求体（脱敏）：

```json
{
  "msgtype": "markdown",
  "markdown": {
    "content": "**高值耗材扫码批次异常**\n> 台次 `OP-SAMPLE-001` · 手术间 `OR-01` · 科室 `SURG-01`\n> 本批共 6 条：已绑定 5 条，异常 1 条\n\n**异常明细**\n> 1. MAT-UNKNOWN-99 数量 1 —— 耗材码不在院内耗材主数据中（`MATERIAL_NOT_REGISTERED`）\n\n> 处理入口：高值耗材扫码计费闭环系统 · 核查清单（护士长 / 高值耗材管理岗）"
  }
}
```

## 5. 消息正文口径

正文只用企业微信 markdown 官方支持的记法：**加粗**、引用块 `>`、行内代码。

| 段落 | 内容 |
|---|---|
| 标题 | `**高值耗材扫码批次异常**` |
| 台次上下文 | 台次号、手术间、科室、扫码枪（行内代码） |
| 计数 | 本批总条数、已绑定条数、异常条数、批内重复条数 |
| 异常明细 | 逐条：耗材码 + 数量 + 中文说明 + **原始 reason_code**（便于与核查清单反查） |
| 处理入口 | 指向核查清单（护士长 / 高值耗材管理岗） |

正文**不含患者可识别字段** —— 耗材码只绑台次，不落到患者。

## 6. 响应体

| 字段 | 类型 | 说明 |
|---|---|---|
| `errcode` | integer | `0` 表示成功；非 0 视为业务失败（`ERR_NOTIFY_BIZ_ERROR`） |
| `errmsg` | string | 错误说明（失败时带在错误信息里） |

## 7. 推送策略

| 规则 | 口径 |
|---|---|
| 无异常批次 | **默认不推**（`onlyAbnormal`，默认 true）：不打扰手术室 |
| 同一批次 | **最多推一条**：批次键落 `notify_delivery` 表（主键唯一），重复投递不再推第二遍 |
| 重复扫码 | 默认不进异常清单（`ignoreDuplicateScan`，默认 true）：那是幂等层的正常结果，台账里本来就有这一笔 |
| 明细条数上限 | 默认 20 条（`maxExceptionItems`），超出折叠为「另有 N 条未列出」 |
| 批次键 | `sha256(台次 \| 手术间 \| 扫码枪 \| 本批条目集合)`：条目集合不变则键不变，批次身份不随结论漂移 |

## 7.5 按台次聚合与去重节流（常驻守护进程的默认口径）

手术室里一台手术扫十几次耗材，**每扫一次推一条**就是十几条消息 —— 群里没人看，
消息一多等于没消息。常驻守护进程因此把「一批一条」改成「**一台次一条**」：

| 规则 | 口径 |
|---|---|
| 聚合窗口 | 默认 30000 毫秒（`NOTIFY_AGGREGATION_WINDOW_MS`）：同一台次的异常在窗口内合并成一条消息，**窗口结束才发出**；期间新到的异常并入同一条 |
| 异常唯一键 | `台次 \| 耗材码 \| 结论`：同一窗口内同一耗材的同一类问题**只出现一次**；重复扫码不重复推（折叠计数写进消息） |
| 窗口键 | `sha256(台次 \| 窗口起点毫秒)`：同一窗口重发时键不变，落 `notify_delivery` 表 → 同一窗口最多推一条 |
| 台次隔离 | 不同台次各开各的窗口，不混消息 |
| 正常批次 | 默认一条都不发（无异常不开窗口） |
| 节流不丢信息 | 窗口内的异常一条不少并进同一条消息，消息体带「待核 N 条」与「重复扫码折叠 N 条」便于核对；异常权威副本在 `check_task`（待核查条目）里 |
| 队列相遇时**合并**不覆盖 | 一条消息发送失败进入退避队列后，同一台次又开了新窗口 —— 两条在待发队列相遇时按**异常唯一键取并集**合并成一条（计数相加、时间窗取最早起最晚止），**先到那条的异常不会被覆盖丢掉**；合并后的窗口键取最早那批的起点，仍算「同一台次一条」 |
| 发送失败 | 失败按退避重新排队（10s 起、指数翻倍、上限 300s），**不丢信息**；台账与核查条目一行不受影响 |
| 停机补发 | 收到 SIGTERM 时，窗口没到期的消息在停机前尽力补发一次 |

聚合模式下的消息正文（markdown）比 §5 多三样：**时间窗**、**该谁处理**、**建议处置**：

```text
**高值耗材扫码待核（台次 `OP-SAMPLE-001`）**
> 手术间 `OR-01` · 科室 `SURG-01` · 时间窗 10:02:30 ~ 10:03:00（30 秒内合并 2 批）
> 本窗口共 8 条耗材：已绑定 5 条，待核 3 条（重复扫码折叠 1 条）

**待核明细（3 条）**
> 1. `MAT-X-01` —— 耗材码不在院内耗材主数据中（`MATERIAL_NOT_REGISTERED`） 数量 1
> 该谁处理：高值耗材管理岗（SURG-01） ｜建议处置：请高值耗材管理岗补建档（导入即生效，无需重启）
```

「该谁处理」与「建议处置」取自责任岗位路由表（`src/check/route.ts`）——
消息里直接给出**该谁管、怎么管**，岗位看完就能动手，不用自己去查原因码。

## 8. 错误码

| 错误码 | 含义 | 通道可达 | 值得重投 | 建议处置 |
|---|---|---|---|---|
| `ERR_NOTIFY_CONFIG` | 地址 / 密钥缺失或非法（请求没发出去） | 否 | 否 | 检查 `WECOM_WEBHOOK_URL`、`WECOM_SECRET` |
| `ERR_NOTIFY_TIMEOUT` | 请求超时 | 否 | 是 | 稍后重推；连续出现查网络 |
| `ERR_NOTIFY_NETWORK` | 连接失败 / DNS 失败 | 否 | 是 | 查 webhook 域名与出口策略 |
| `ERR_NOTIFY_HTTP_5XX` | 对端 5xx | 是 | 是 | 稍后重推；连续出现查企微侧状态 |
| `ERR_NOTIFY_HTTP_4XX` | 对端 4xx | 是 | 否 | 地址或 key 不对，核对 `WECOM_WEBHOOK_URL` |
| `ERR_NOTIFY_RESPONSE_INVALID` | 响应不是合法 JSON | 是 | 是 | 确认 webhook 地址指向企微机器人 |
| `ERR_NOTIFY_BIZ_ERROR` | 对端返回 `errcode ≠ 0` | 是 | 否 | 按 `errmsg` 处置（如 key 失效、机器人已解散） |
| `ERR_NOTIFY_INTERNAL` | 本侧内部异常 | 否 | 是 | 看结构化日志定位 |

## 9. 失败不阻塞台账落库

推送是**通知**，不是业务状态推进的主路：

- 推送失败被捕获，**不抛到主流程** —— 扫码事件的逐条回执照常返回；
- 失败计数写进审计链（立即推送模式 `event_type = notify_batch_failed`；聚合模式 `event_type = notify_window_failed`，`detail` 带错误码与窗口键）；
- 聚合模式发送成功另记一行 `notify_window_sent`（带窗口键、条目数、折叠数），可回放「哪台次什么时候说了什么」；
- 推送台账 `notify_delivery` 记一行 `failed`，供 `doctor` 展示与运维排查；
- 台账行数、核查条目数**一行都不变**。

## 10. 联调自检

```bash
# 1) 凭据齐否（只报齐否，不报明文）

# 2) 推送失败计数
node dist/cli.js summary
```
