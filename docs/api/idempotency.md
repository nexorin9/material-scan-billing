# 幂等键档位与批号维度

> 手术室里的同一条扫码会被**反复投递**：扫码枪重扫、网关重传、网络抖动后的补投。
> 幂等键就是防住「同一笔消耗被计费两次」的那把尺子。这份文档说清三件事：
> 键由哪几个维度派生、院内有哪两档口径（`v1` / `v2`）、升级前写下的老账怎么认。

## 一、键派生：档位写在最前面

幂等键 = `sha256("<档位>|<耗材码>|<台次>[|<批号>]")`，十六进制小写。

| 档位 | 参与哈希的原文 | 业务含义 | 谁在用 |
|------|----------------|----------|--------|
| `legacy` | `耗材码\|台次` | 历史格式：**只读**，程序不再新写 | 升级前写下的台账行与占位行 |
| `v1` | `v1\|耗材码\|台次` | 同一耗材同一台次**只算一次**（批号不参与） | 默认档位（`IDEMPOTENCY_KEY_PROFILE=v1`） |
| `v2` | `v2\|耗材码\|台次\|批号` | 同一耗材同一台次的**不同批号各算一次** | 需要按批号细分的科室 |

档位写在原文最前面 → **键自带版本号**：迁移期新旧两代键可以并存，
老键不会被新口径误判成同一笔。

### 与时间戳无关（硬不变量）

键**不**掺入扫描时间、重试次数、扫码枪编号：

- 掺了扫描时间 → 网关重投一次就是一笔新账；
- 掺了重试次数 → 重试机制本身就会造出重复计费；
- 掺了扫码枪编号 → 换一把扫码枪重扫同一件就要再计一笔。

三档都成立（`tests/idempotency-profile.test.ts` 逐档断言）。

### v2 缺批号怎么办

v2 档位但扫码事件**没带批号**（老设备只扫 GTIN、没扫 (10) 生产标识）时，
键**降级成 v1**（`batch_missing = true`），台账行的键档位也记成 v1。

理由：批号未知就分不清「同一批重扫」和「另一批的同款耗材」。
宁可按 v1 只算一次（少算，绝不重复计费），也不冒重复计费的风险。

## 二、两档口径下的判定结果

| 场景 | `v1` | `v2` |
|------|------|------|
| 同码 + 同台次 + 同批号，重投 | 判重复（`DUPLICATE_SCAN`），台账 1 行 | 同左 |
| 同码 + 同台次 + **不同批号** | 判重复，原因码 `DUPLICATE_SCAN_BATCH_MISMATCH`（台账 1 行） | **各算一次**：台账 2 行、各触发一次计费 |
| 同码 + 同台次 + 批号缺失 | 判重复 | 降级按 v1 判重复 |
| 换扫码枪重投同一笔 | 判重复 | 判重复（键与扫码枪编号无关） |

`DUPLICATE_SCAN_BATCH_MISMATCH` 的意思是「同款耗材的两批撞在同一台次上了」：
- 若确实是两笔真实消耗 → 把档位切到 `v2` 后重投；
- 若不是 → 忽略即可（**不会产生第二行台账，也不会触发第二次计费**）。

## 三、配置

```bash
# 环境变量（不配 = v1）
IDEMPOTENCY_KEY_PROFILE=v1
```

- 允许取值：**`v1` / `v2`**；
- 配成别的值 → **启动即报错**（`ERR_INVALID_CONFIG`，指名变量名），
  启动自检里「幂等键档位」这一项判不通过、进程拒绝启动；
- 档位决定「同一耗材同一台次算几笔」，配错就是重复计费或多计费，
  所以**默认值只在没配的时候用**，配错不兜底。

切换档位不需要停机重启以外的任何操作：改完环境变量重启守护进程即可，
台账里已有的行按各自档位继续算（两档键并存）。

## 四、升级前的老账怎么办

升级前写下的台账行，键是 `legacy` 格式（`sha256(耗材码|台次)`），
字节与新程序的 v1 键不同。台账迁移的 **v11 版**（`binding_key_versioning`）会：

1. 给台账行补 `batch_no` 列（v2 的去重维度落在行上，事后查得到「哪一批」）；
2. **认领历史行**：按 legacy 原文重算每行的键，对得上的行标成 `legacy` 档位；
3. 重建唯一防线：
   - `legacy` + `v1` → 同码同台次只许一行（老行与新行互相挡住）；
   - `v2` → 同码同台次**同批号**只许一行（不同批号可以各记一行）。

因此：**老行不会被当成新事件再计一笔**（维度级重复判定先查台账行，
再走幂等键占位），而 v1 / v2 两版键在同一台账里可以并存。

## 五、出站侧的口径（键与档位一并透传给 HIS）

HIS 计费明细的字段规范见 `docs/api/his-charging.md`。明细**没有批号字段**：

`uses:[{material_code, quantity, price_code, use_time, fee_category, medical_insurance_class,
idempotency_key, key_profile}]`

所以 `v2` 档位下同款耗材的两个批次，在出站报文里是**两行同码明细**
（一行台账对应一行明细，逐条回执按行对齐）。
对端按项目合并成数量 2 是对端的事；**批号维度落在台账行与核查包里**，
批次差异查得到、核对得清。

### 5.1 两把键：行级与请求级

| 层 | 字段 | 派生口径 | 挡的是 |
|---|---|---|---|
| 行级 | `uses[].idempotency_key` | `sha256("<档位>\|<耗材码>\|<台次>[\|<批号>]")` | 同一条耗材消费被计费两次 |
| 请求级 | `idempotency_key` | `sha256("req\|<台次号>\|<行级键1>\|<行级键2>…")`（行级键升序入哈希） | 同一个请求被送两遍 |

两把键都**与时间戳、重试次数、扫码枪编号无关**：重投时复用同一把键，
对端据此认得「这是同一笔」，不去重就会记两笔账。

### 5.2 对端不回显键怎么办

对端**可以**回显收到的键（逐条回显行级键、顶层回显请求级键）。
回显与否不影响本侧闭环：

| 回执字段 `peer_idempotency_status` | 含义 | 本侧怎么办 |
|---|---|---|
| `ECHOED` | 对端回显了同一把键 | 对端已启用幂等去重，照常推进台账状态 |
| `NOT_ECHOED` | 对端没回显（**对端未启用幂等**） | 本侧仍保证单侧幂等（台账唯一键 + 幂等占位层）；重复投递的责任不在对端，核查时留意 |
| `MISMATCH` | 对端回显了另一把键 | 两端口径不一致，如实留痕交信息科与对端确认；**不误判成重复计费** |

### 5.3 切换档位对老账的影响

键档位由配置项 `IDEMPOTENCY_KEY_PROFILE` 决定，**只影响新写的账**：

- 已经绑上台账的行按**行上的键**透传，档位跟着那一行走（老账不会被新档位改写）；
- 没有台账键、现派生的条目按当前档位派生（`v2` 缺批号时降级成 `v1`，宁可少算）；
- 请求级键由行级键派生，行级键不变 → 请求级键也不变 → 重投始终复用同一把键。

## 六、验收

```bash
node --test dist/tests/idempotency-profile.test.js
node --test dist/tests/outbound-idempotency.test.js
```

前者覆盖：两档派生口径、键自带档位、键与时间戳 / 重试次数 / 扫码枪编号无关、
v2 缺批号降级、配置项校验与启动自检、v1 / v2 各自的判定分支、
老行不被误判为新事件、迁移 v11 的历史行认领与唯一防线口径。

后者覆盖：出站请求体带行级与请求级两把键、行级键与台账行逐字一致、
重投两次请求体键逐字相同、回执行落库带键与对端回显状态、
切换档位后键值不同、对端回显 / 不回显 / 回显异值的三种标注、迁移 v18 落两列。
