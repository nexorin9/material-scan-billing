# 事件日志与溯源

> 设备事件是排查问题的一手材料 —— 原始报文一旦不落盘就没法复盘。
> 这份文档说清四件事：**落了什么**（表结构）、**怎么回查**（三条查询路径）、
> **留多久**（保留策略）、**清了什么**（清日志不清账）。

## 一、落了什么：事件日志一行 = 一次设备投递

事件日志表 `scan_event` **只增不改**（与审计链同口径：「发生过什么」是事实，不许改写）。

| 字段 | 含义 | 备注 |
|------|------|------|
| `id` | 自增行号 | 落库顺序 = 到达顺序 |
| `request_id` | **本次投递的标识** | 一次扫码投递 = 一个标识；事件日志、台账行、审计行三边共用 |
| `received_at` | 收到时刻（ISO） | 按**收到**筛，不是按落账筛：运维要的是「那段时间设备报了什么」 |
| `source` | 来源路 | `scanner_http`（扫码枪 HTTP）/ `rfid_dir`（RFID 目录投递） |
| `operation_no` | 台次号 | 事件自带的台次 |
| `room_no` | 手术间 | |
| `scanner_id` | 扫码枪 / 网关编号 | |
| `raw_body` | **原始报文，逐字保留** | 设备报了什么，一字不改；重放与复盘都靠它 |
| `normalized_json` | 归一后的批次信封 | 台次 + 手术间 + 扫码枪 + 条目（码制已归一，原始码保留在条目里） |
| `signature_verified` | 签名是否验过 | 目录投递路无签名，恒为 0 |
| `idempotency_key` | 关联幂等键 | 单条事件才有；批次级事件留空 |
| `conclusion` | 本批结论分布 | 形如 `accepted=5;rejected=1` |
| `batch_id` | 设备侧那一批的号 | 扫码枪路 = 投递标识；目录路 = 批次文件名。重放按批次选区间用它 |
| `created_at` | 落账时刻 | 与 `received_at` 可能不同（重放不写事件日志，所以两者不会互相污染） |

### 不落什么

事件日志**不落患者可识别明细**。原始报文里只有耗材码、台次号、手术间、扫码枪 ——
耗材码与台次号保留原值（事后核对要用），患者标识从来不在这一层。

### 耗材码关联表

事件日志一行是**一批**（一批 5–8 条耗材），「这个码都出过什么事」要能反查是哪几批，
所以另立关联表 `scan_event_material`：

| 字段 | 含义 |
|------|------|
| `event_id` | 事件行 id |
| `material_code` | 耗材码 |
| `code_kind` | `canonical`（归一后的院内码）/ `raw`（设备上印的原始码） |

原始码与归一码相同只挂一条 —— 查「这个码」不该看到同一条事件两遍。
**设备上印的那串码（UDI / GS1）也能反查**：排障时信息科手里通常只有其中一种。

## 二、怎么回查：三条路径

### ① 按投递标识三向回查

一个 `request_id` 串起三边（`node dist/cli.js events --request <标识>`）：

```
事件日志（设备报了什么）→ 台账条目（这一批落了哪几行账）→ 审计链（后来怎么处置的）
```

- 事件行：`scan_event.request_id`
- 台账行：`material_binding.request_id`（迁移 v25 补的列）
- 审计行：`audit_chain.request_id`（迁移 v7 起就有）

### ② 按耗材码回查事件序列

```
node dist/cli.js events --material MAT-SAMPLE-01
```

返回该码出现在**哪些批次**里，按收到时刻升序。原始码与院内码都能查。

### ③ 按台次 / 来源 / 时间窗回查

```
node dist/cli.js events --operation OP-SAMPLE-001
node dist/cli.js events --source rfid_dir
```

时间窗筛选走 `received_at`（收到时刻），口径见 `docs/api/replay.md`。

## 三、留多久：双阈值保留策略

事件日志会一直长（常驻进程每天都在收）。保留策略是**双阈值**：

| 阈值 | 配置项 | 默认值 | 含义 |
|------|--------|--------|------|
| 保留期 | `EVENT_LOG_RETENTION_DAYS` | 30 天 | 比这更旧的事件行清掉 |
| 最大行数 | `EVENT_LOG_MAX_ROWS` | 100000 行 | 超了就按最旧清到上限 |
| 执行周期 | `EVENT_LOG_CLEANUP_INTERVAL_MS` | 3600000 ms | 守护进程多久跑一次 |

执行顺序：**先按保留期清过期行 → 剩下的还超上限再按最旧清**。
关联行（事件 ↔ 耗材码）跟着一起清，不留悬空引用。

## 四、清了什么：清日志，不清账

清理**只动事件日志**（`scan_event` + `scan_event_material`）：

| 不受影响 | 说明 |
|----------|------|
| 耗材使用台账 `material_binding` | 业务账，一行不动 |
| 计费回执 `charge_receipt` | 已回写的计费事实 |
| 核查任务 `check_task` | 人工待办 |
| 审计链 `audit_chain` | 只增不改的处置轨迹 |

### 清理留痕

真的清掉行就在审计链追加一行 `event_log_pruned`，写清清了多少、按什么阈值清的：

```json
{
  "removed_expired": 30,
  "removed_overflow": 12,
  "removed_total": 42,
  "remaining": 100000,
  "cutoff_at": "2026-10-04T00:00:00.000Z",
  "max_rows": 100000,
  "retention_days": 30
}
```

内审与飞检问「日志怎么少了」时有据可查（`node dist/cli.js ledger` 之外的审计链查询）。

## 五、边界与口径

- **事件日志不是台账**：它是「设备报了什么」的原始记录，不是业务账；查账走台账。
- **重放不写事件日志**：`replay` 走的是生产同一条结算路径，但 `logEvent=false` ——
  否则每重放一次日志就长一截，越重放越多，没法核对。
- **重复扫码照样各留一行事件**：幂等键挡的是**重复计费**，不是挡记录 ——
  「这一码被扫了几次」本身就是要查的事。
- **保留期到点即清**：留太久的事件不再可查（这是可配的默认值，不是硬规则）。
