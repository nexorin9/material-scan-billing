# 错误码对照表

> 手术室里的常驻进程没人盯着终端，出问题时信息科要能在一条命令里看清「**哪一路、哪个台次、哪一条耗材、失败在哪个错误码**」。这张表就是那套话术的字典。

## 这张表怎么用

- **同一个码出现在三个地方**：结构化日志的 `error_code` 字段、核查条目（`check_task.error_code`）、计费回执行（`charge_receipt.error_code`）。在核查清单上看到 `ERR_MATERIAL_NOT_REGISTERED`，去日志里搜同一个码，就能定位到那一条耗材。
- **业务原因码 → 统一错误码**由 `src/log/error-codes.ts` 的 `REASON_TO_ERROR_CODE` 统一映射，业务层不自己拼错误码。业务原因码（如 `MATERIAL_NOT_REGISTERED`）仍然逐条落库，保留「为什么」的细节。
- **「可重投」是这张表最重要的一列**：可重投的进指数退避队列（等对端恢复）；不可重投的直接转人工核查条目 —— 对端拒收的东西重投一万次也是拒收，白白占住手术室的时间。
- **未知码按「不可重投 + 需人工」处理**（fail safe）：对端回执里出现本表没登记的码时，先转人工并把原始码登记进本表，**不默认当作可重投**。
- **对端回执码另有专表**：HIS 计费侧回执里的 `reason_code`（价码不存在 / 医保分类不匹配 / 台次不存在 / 数量超限 / 库存不足 / 对端限流 …）按「可重投 / 不可重投 / 需人工」三档处置，见下文「计费回执 reason_code 处置判定表」。

## 排查顺序

`排查顺序` 数字小的先排 —— 按「先排哪一路最省时间」排：

| 区间 | 环节 | 典型现象 |
|------|------|----------|
| 5–19 | 运行期凭据 / 入站接入 | 设备连不上、签名对不上、时间戳过期 |
| 20–29 | 入站报文格式 | 报文不是合法 JSON、字段缺失、请求体过大 |
| 30–49 | 绑定判定 / 并发幂等 | 台次查不到、耗材未建档、跨台次重复、占位未释放 |
| 50–59 | 台账状态 / 费用与医保口径 | 非法状态迁移被拒；费用类别或医保分类口径不合规 |
| 60–69 | 计费回写 | 计费超时、对端业务拒绝、回执结构不符 |
| 70–72 | 核查闭环 | 核查条目状态不对（已落定 / 不可撤回） |
| 73–79 | 对账差异 | 台账有、计费侧没记账（超时待重投 / 业务拒绝 / 口径不一致 / 对端多出来一条） |
| 80–89 | 企业微信推送 | 推送失败（**不影响台账落库**） |
| 90+ | 内部错误 | 保留日志与审计链，联系信息科 |

计费回写这一段（60–69）内部再分三档，按「先排哪一档最省时间」：

| 档位 | 排查顺序 | 典型现象 | 先做什么 |
|------|----------|----------|----------|
| 通道暂时不可用（可重投） | 60–62 | 超时、连不上、5xx、对端限流 / 服务繁忙 / 临时库存锁 | 先等退避重投自愈；持续出现再找对端查该时段负载 |

计费通道这一档内部还分**两个阶段**（排障时先分清是哪一段）：
`ERR_CHARGE_CONNECT_TIMEOUT` 是**连接没建起来**（看地址、端口与院内网络策略）；
`ERR_CHARGE_TIMEOUT` 是**已经连上、对端迟迟不给结论**（看 HIS 计费侧负载）。
连续失败达阈值时通道会**熔断**（`ERR_CHARGE_CIRCUIT_OPEN`）：这段时间请求不再外发，
条目留在退避重投队列里等通道恢复，`doctor` 能看到当前是否熔断、下次探测时间。
| 对端要求人判断（需人工） | 63 | 医保规则冲突、特殊耗材待审批、收费员权限不足、疑似重复计费 | 转医保办 / 耗材管理岗 / 收费员，**别让程序替人判** |
| 对端明确不收（不可重投） | 64 | 价码不存在、医保分类对不上、库存不足、台次在计费侧不存在 | 改耗材主数据 / 同步对端，再由人工重投 |

## 计费回执 reason_code 处置判定表

HIS 计费侧回执里带回来的 `reason_code` 决定这条耗材**要不要重投、重投有没有意义**。
本表把每个码钉死到一档（真源：`src/charge/reason-codes.ts`），代码里不再出现「看情况」：

| 处置档位 | 含义 | 落到哪 |
|----------|------|--------|
| **可重投** | 对端暂时收不了或收得慢（限流、服务繁忙、库存临时锁）；再发一次会得到不同结论 | 进指数退避队列，重投复用同一把幂等键 |
| **不可重投** | 对端明确不收，且**改了主数据才会变**（价码不存在、医保分类对不上、库存不足） | **立即**转核查任务，不做无谓重试 |
| **需人工** | 对端要求人判断（医保规则冲突、特殊耗材审批、疑似重复计费） | 转核查任务并标注，等护士长 / 医保办 / 收费员落定结论 |

**未知码按「不可重投 + 需人工」处理（fail safe）**：对端回执里出现本表没登记的码时，
先转人工，并把原始码登记进错误码表待补项（`registerPendingErrorCode`）与审计链
（`charge_reason_code_unknown`），**不默认当作可重投** —— 对本侧没读懂的东西重投，
可能在计费侧造成重复记账。

| 回执码 | 中文含义 | 处置档位 | 统一错误码 | 建议处置 | 是否常见 |
|--------|----------|----------|------------|----------|----------|

## 台次归属双因子（ERR_OPERATION_CONFLICT 的判定口径）

扫码事件带的是**事件自己说的**手术间，排台带的是**排台说的**手术间。两个说法对不上，可能是台次号挂错台、扫码枪挪了间、或者有人拿别人的枪扫 —— 绑错台就是错账，所以**任一因子对不上就一律拒绝、转人工，绝不按单一因子猜绑**。

| 因子 | 比对的两侧 | 科室上下文从哪来 | 不一致时的结论 |
|------|------------|------------------|----------------|
| 手术间 `room_no` | 事件手术间 ↔ 排台手术间 | 事件必带（入站报文字段 `room_no`） | `OPERATION_ATTRIBUTION_CONFLICT` / `ERR_OPERATION_CONFLICT` |
| 科室 `dept_code` | 事件科室上下文 ↔ 排台科室 | 优先取事件自带的科室；没带就取**扫码枪位置登记簿**里登记的科室（枪固定在哪间手术间，那间就属于某个科室 —— 与手术间相互独立的第二个因子） | 同上 |

**扫码枪位置登记簿**（环境变量 `OR_SCANNER_REGISTRY`，格式 `扫码枪编号=手术间[,科室]`，多条用 `;` 分隔）还额外核一次**配置漂移**：登记簿说这把枪在 A 间，事件却说自己来自 B 间 —— 说明枪挪了间 / 登记过期 / 事件根本不是这台枪发的。这条单独在审计链留一行 `scanner_config_drift`，并按归属冲突处理（即便事件手术间与排台碰巧一致，也不放行）。

**处置口径**：

1. 核对排台：台次号与手术间、科室的对应关系是不是写错了（改排台后重扫即可）；
2. 核对登记簿：扫码枪是不是挪过间（挪了就要更新 `OR_SCANNER_REGISTRY`）；
3. 两侧都对得上仍然冲突时，走人工落定结论 —— **本系统不自动改台、不自动补录**。

**两侧的值都留了痕**，事后能核对「当时到底对的是哪两个手术间」：

| 台账 | 事件侧 | 排台侧 |
|------|--------|--------|
| `material_binding` | `event_room_no` / `event_dept_code` | `master_room_no` / `dept_code` |
| `check_task` | `event_room_no` / `event_dept_code` | `master_room_no` / `master_dept_code` |

老行（升级前写的）这几列留空 —— 留空即「当时没做过归属核对」，不补值（补一个看起来核对过的值等于伪造事实）。

## 怎么按码排查（信息科三步走）

1. **在核查清单里看码**：护士长在核查条目上看到的是同一个码，它告诉你这件事属于哪一路、该不该重投。
2. **在日志里按码搜**：日志每行一个 JSON，`error_code` 字段可直接过滤：

   ```bash
   # 从日志里捞出所有「耗材未建档」的条目，按台次看
   grep '"error_code":"ERR_MATERIAL_NOT_REGISTERED"' daemon.log | jq -r '[.timestamp, .operation_no, .material_code] | @tsv'
   ```

3. **在本表里查处置口径**：照「建议处置」那一栏做，做完在核查条目上落定结论并回写台账。

```bash
# 查某个码的中文含义与处置口径
node -e "import('./dist/src/log/error-codes.js').then(m => console.log(m.describeErrorCode('ERR_CHARGE_BUSINESS_REJECTED')))"
```

## 日志字段对照

每行日志都是一行 JSON，固定字段如下（缺值为 `null`，便于按字段检索）：

| 字段 | 含义 | 什么时候有值 |
|------|------|--------------|
| `timestamp` | 事件发生时刻（UTC ISO 8601） | 永远有 |
| `level` | `debug` / `info` / `warn` / `error` | 永远有 |
| `service` | 服务名 | 永远有 |
| `request_id` | 投递标识（一批一次） | 入站与结算日志有 |
| `channel` | 哪一路：`inbound` / `binding` / `outbound` / `notify` | 永远有 |
| `operation_no` | 台次号 | 涉及台次的日志有 |
| `material_code` | 耗材码 | 逐条日志有 |
| `conclusion` | 绑定结论（`BOUND` / `NOT_REGISTERED` / `CROSS_OP_DUP` / `CLOSED` / `CHARGE_REJECTED`） | 逐条日志有 |
| `error_code` | 统一错误码（见本表） | 异常时才有 |
| `duration_ms` | 本次处理耗时（毫秒） | 有耗时的日志有 |
| `message` | 一句话说明（人话） | 永远有 |

**凭据明文一律不出现在日志里**：字段名里带 token / secret / authorization / webhook 的值一律打码成 `***`；启动时登记的三路凭据位即使被拼进 `message`，也会被打码。
