# 出站载荷清洗口径（编码 · 字符 · 必填 · 长度）

> 院内导出的耗材主数据是脏的：老系统导 GBK、新系统导 UTF-8，耗材名里带着「髋」「钛」这类生僻字，价码偶尔多一个全角括号或零宽字符，导出工具还会把整列留空。
> 这张纸写清楚**这些脏数据进计费载荷之前会被怎么处理**，以及处理不了的时候**错在哪个码、人要做什么**。

## 清洗发生在哪一步

```
主数据 CSV（可能是 GBK）
   │  ① 编码归一：UTF-8 → GBK 解码，解不出 → 保留原始字节并报错
   ▼
院内主数据镜像（operation / material）
   │  ② 判定：台次 × 耗材 × 归属（双因子）
   ▼
耗材使用台账（material_binding）
   │  ③ 出站载荷清洗：字符归一 → 必填校验 → 长度前置判定
   ▼
HIS 计费请求（material-uses）
```

第 ③ 步就在**组装载荷的那一刻**（`src/charge/sanitize.ts`），不是等到发出去被对端拒了才处理。

## 三条硬约束

| 约束 | 口径 | 对应错误码 |
|------|------|------------|
| **编码解不出就拒，不糊弄** | UTF-8 与 GBK 都解不出时**保留原始字节**报错；绝不用替换字符（U+FFFD）把乱码拼成「看起来像文本」 | `ERR_CHARGE_ENCODING_UNDECODABLE` |
| **缺字段就拒，不填默认值** | 台次号 / 科室编码 / 耗材码 / 价码 / 数量任一为空 → 拒**那一条**（请求级字段为空则整批发不出去），不拿默认值糊过去 | `ERR_CHARGE_FIELD_MISSING` |
| **身份性字段不静默改写** | 耗材码 / 价码归一后会变成**另一个码 / 另一个价码** → 本地拒收转人工，绝不「改好了再照发」 | `ERR_CHARGE_CODE_NOT_CANONICAL` |

## ① 编码归一：怎么判断这份字节是 GBK 还是 UTF-8

不能简单地「UTF-8 解不出来就当 GBK」—— GBK 的字节流**有可能**恰好是合法的 UTF-8：

- 「中文」两个字的 GBK 字节是 `D6 D0 CE C4`；
- UTF-8 严格解码它**不报错**，但解出来的是希腊字母 `U+0590` 与 `U+0384`；
- 这种「解得出来但解错了」最危险 —— 乱码会一路流到计费侧。

所以本系统的口径是**两个候选都解一遍，再按可读性择优**：

| 判据 | 口径 |
|------|------|
| 中文字符（统一表意文字 / 扩展 A / CJK 标点） | 每个 **+2** |
| 「解错了」的字符区（希腊 / 西里尔 / 希伯来 / 阿拉伯 / 私用区 / 替换字符） | 每个 **−4** |
| 其余非 ASCII 字符 | 每个 **−1** |
| 打平时 | 以 UTF-8 为准（它是接口与 JSON 的标准编码） |

编码策略可配（环境变量 `MASTER_DATA_ENCODING`）：

| 取值 | 口径 |
|------|------|
| `auto`（默认） | 上面的择优口径 |
| `utf-8` | 只认 UTF-8；解不动即拒 |
| `gbk` | 只认 GBK；解不动即拒（老系统导出固定 GBK 时可以锁死，避免误判） |

取值非法 → **启动即报错**并指名变量名（`ERR_INVALID_CONFIG`），不在运行期才炸。

## ② 字符归一：改什么、不改什么

| 动作 | 口径 |
|------|------|
| 全角转半角 | `！`～`～`（U+FF01–U+FF5E）逐个转成半角；表意文字空格（U+3000）转成半角空格 |
| 去不可见字符 | C0 / C1 控制字符、零宽字符（U+200B–U+200F）、BOM（U+FEFF）、软连字符（U+00AD） |
| 折叠连续空白 | 连续空格 / 制表符折成一个，首尾空白去掉 |

**不改**的：大小写、中文用字、合法标点。归一只解决「同一样东西的两种写法」，不替人改内容。

### 身份性字段 vs 描述性字段

| 字段 | 归一后与原值不同怎么办 | 为什么 |
|------|----------------------|--------|
| `material_code` / `price_code`（身份性） | **本地拒收**，转人工（`ERR_CHARGE_CODE_NOT_CANONICAL`），照发的仍是原值 | 归一后的码就是**另一个耗材 / 另一个价目** —— 照发就是记错账；台账里也说不清改过哪里 |
| `fee_category` / `medical_insurance_class`（描述性） | 按归一后的值发出，**归一前后对照落台账** | 这是口径标签，里面的零宽字符与全角括号属于同义写法，归一后语义不变 |

幂等键（`idempotency_key`）**不参与归一** —— 键是去重的身份，改一个字节就是另一把键。

## ③ 归一前后对照落台账

台账行 `material_binding.sanitize_trace` 存一份 JSON（历史行留空 = 落库时还没有这一层清洗）：

```json
{
  "changed": true,
  "fields": [
    { "field": "price_code", "before": "PR-001​", "after": "PR-001​",
      "normalized": "PR-001", "changed": true, "actions": ["strip_invisible"] }
  ]
}
```

- `before` = 台账里的原值；
- `after` = 实际发出去的值（身份性字段 = 原值）；
- `normalized` = 归一后的值 —— 身份性字段被拒时，这一列告诉耗材管理岗「规范写法应该是什么」。

事后对账时如果 HIS 计费侧收到的耗材码与台账里长得不一样，靠这一列就能回答「是主数据改了，还是清洗改了」。

## ④ 长度上限：归一之后再判

长度判定在归一**之后**做（归一会改变长度：去零宽字符会变短）。上限表复用出站契约的同一张表，不另立一套口径：

| 字段 | 上限（字符） |
|------|------------|
| `operation_no` | 64 |
| `dept_code` | 32 |
| `material_code` | 32 |
| `price_code` | 32 |

超长即拒（`ERR_CHARGE_FIELD_TOO_LONG`），**不截断后照发** —— 截断过的耗材码就是另一个耗材。

## 错误码与处置

| 错误码 | 中文含义 | 可重投 | 建议处置 |
|--------|----------|--------|----------|
| `ERR_CHARGE_ENCODING_UNDECODABLE` | 载荷编码解不出来（UTF-8 与 GBK 都不合法），原始字节已保留 | 不可重投 | 核对导出方给的文件到底是什么编码，或配置 `MASTER_DATA_ENCODING`；本系统不做替换字符糊弄，解不出即拒 |
| `ERR_CHARGE_FIELD_MISSING` | 出站计费必填字段为空（台次号 / 科室编码 / 耗材码 / 价码 / 数量） | 不可重投 | 核对主数据与扫码上报，补齐后由人工重投；不填默认值、不发半截单据 |
| `ERR_CHARGE_CODE_NOT_CANONICAL` | 耗材码 / 价码写法不规范（归一后会变成另一个码或另一个价码） | 不可重投 | 核对主数据里的耗材码 / 价码是否含全角字符或不可见字符，由耗材管理岗改成规范写法后重投 |
| `ERR_CHARGE_FIELD_TOO_LONG` | 出站计费字段超出长度上限 | 不可重投 | 核对主数据里的耗材码与价码长度；不截断后照发，修正后由人工重投 |

被拒的条目**照样有回执、有核查条目**：台账行数与回执行数守恒（提交几条就有几条结论），条目状态转 `check_pending`，等人工落定。
