# 并发同键串行化与租约争用压测

> 同一条耗材扫码并发投递 200 次 —— **幂等版**台账 1 行、
> 计费 1 次、对端收到 **0 条**重复计费；
> **朴素基线**台账 130–167 行（竞态结果，见下）、对端收到 **129–166 条**重复计费。
> 幂等层至少省下 **129 条**重复计费。

## 跑法

```bash
# ① 幂等版并发压测 + 租约争用 + 朴素基线对照（产物：data/bench/concurrency.json）
node dist/scripts/bench-concurrency.js --concurrency 200

# ② 单独跑朴素基线（产物：data/bench/concurrency-naive.json）
node dist/scripts/baseline-naive.js --concurrency 200 --gap-ms 30

# 一次跑完（等价）
npm run bench:concurrency

# 只跑阈值断言（CI 用小样本）
node --test dist/tests/concurrency.test.js
```

## 三个场景

| 场景 | 投递方式 | 幂等层 | 期望 |
|------|----------|--------|------|
| ① 幂等版并发压测 | 200 次**并发** HTTP 投递同一条扫码 | 幂等占位（claim → confirm） | 台账 1 行、计费 1 次、对端 0 条重复计费 |
| ② 租约争用 | 先占位不确认，再 20 次并发投递，租约到期后再投 1 次 | 幂等占位 + 租约到期接管 | 争用期全部 busy；接管后台账 1 行、计费 1 次 |
| ③ 朴素基线 | 同 200 次**并发** HTTP 投递同一条扫码 | **无**（查不到就写） | 台账多行、对端出现重复计费（条数是竞态结果，见下） |

并发投递的 200 次里，**只有扫码时间 / 扫码枪编号 / 批号在变**，耗材码与台次不变 ——
幂等键派生自「耗材码 + 台次」，与这三者无关（键实测值 `2bfe043398c75591…`）。

## 朴素基线的重复条数是竞态结果（非确定）

朴素基线「先查后写」之间有 30 ms 的异步间隙，**有多少个请求在第一个请求落库之前
通过查重，取决于当时的调度** —— 所以重复条数每次跑都不一样。同一份代码连续跑 3 次：

| 运行 | 耗材使用台账行数 | 出站计费明细条数 | 对端收到的重复计费条目 |
|------|------------------|------------------|------------------------|
| 第 1 次 | 167 | 167 | 166 |
| 第 2 次 | 130 | 130 | 129 |
| 第 3 次 | 130 | 130 | 129 |

区间：台账 130–167 行、重复计费 129–166 条。

**读法**：区间下界（129 条）已经说明问题 —— 少则一条都不重复，多则接近全部 200 条都重复。
关键是**幂等版那一列恒定**：无论调度怎么变，台账 1 行、计费 1 次、
对端重复计费 0 条，一次都不多。

## 对照结果

| 指标 | 幂等版（本产品） | 朴素基线（有异步间隙） | 朴素基线（无间隙） |
|------|------------------|------------------------|--------------------|
| 并发投递次数 | 200 | 200 | 200 |
| 查重与写库之间的异步间隙 | 无（占位在 await 之前完成） | 30 ms | 0 ms |
| 耗材使用台账行数 | **1** | 130–167 | 1 |
| 其中重复落行 | 0 | 129–166 | 0 |
| 绑上（bound）响应数 | 1 | 167 | 1 |
| 被拒：租约忙（CLAIM_BUSY） | 0 | 0 | 0 |
| 被拒：重复扫码（DUPLICATE_SCAN） | 199 | 33 | 199 |
| 出站计费请求次数 | 1 | 2 | 1 |
| 出站计费明细条数 | 1 | 130–167 | 1 |
| 对端收到的明细条数 | 1 | 167 | 1 |
| **对端收到的重复计费条目** | **0** | **129–166** | 0 |
| 并发投递耗时 | 83.12 ms | 89.51 ms | 45.56 ms |

三列跑的是**同一批并发投递**、**同一个出站客户端**、**同一个计费替身**、**同一条计费回写路径**
（`writeBackOperationCharges`），差别只在「有没有幂等占位层」以及那个 await 间隙。
朴素基线那一列给的是 3 次运行的**区间**（竞态结果，非确定）；幂等版那一列是**恒定值**。

## 幂等版实测明细

```text
并发投递 200 次同一条耗材扫码
HTTP 200 响应 200 次 / 非 200 0 次
绑上（bound）1 次（应当只有 1 次）
被拒：租约忙 0 次 / 重复扫码 199 次 / 其他 0 次
耗材使用台账 1 行
关台回写：出站请求 1 次 / 明细 1 条
对端收到明细 1 条 / 重复计费 0 条
并发投递耗时 83.12 ms
```

## 租约争用实测明细

持有者占位（租约 2000 ms）后不确认，随后 20 次并发投递：

```text
争用窗口内的并发投递：20 次
  拿到 busy（CLAIM_BUSY，不重复处理、不重复计费）：20 次
  绑上（应当为 0）：0 次
  争用窗口内产生的计费请求（应当为 0）：0 次
租约到期后接管：绑上 是（原因码 -）
接管后台账 1 行 / 出站计费请求 1 次 / 明细 1 条
对端收到的重复计费条目：0 条
占位 claim_count：2（接管一次 +1；台账仍只有 1 行）
总耗时 2058.02 ms
```

读法：租约不是永久锁 —— 持有者卡住时，后来者拿到 **busy**（不重复处理、不重复计费）；
租约到期后其中一个**接管**并完成结算（claim_count 递增，看得出被重试过几次），
但台账仍然只有一行、计费仍然只有一次。

## 口径与局限（务必一起看）

- **重复计费来自那个 await 间隙，不是来自「没做查重」本身**：朴素基线还跑了一个
  **无间隙**变体（`--gap-ms 0`，查重与写库在同一个同步块里）——
  此时台账 1 行、重复计费 0 条。
  有间隙时是 130–167 行 / 129–166 条。
  也就是说：**只要「查重」和「写库」之间有任何一个 await，朴素的先查后写就会重复计费**；
  幂等占位层把占位放在任何 await 之前，用**一把租约**把并发窗口关掉。
- **朴素基线的重复条数是竞态结果，不是定值**：有多少个请求在第一个请求落库之前通过查重，
  取决于当时的调度，因此同一份代码每次跑出来的数字都不同（本文给的是 3 次运行的区间）。
  **不要把某一次的数字当成基线**；要看的是「幂等版那一列恒定、朴素版那一列不为零」。
  幂等版的数字之所以恒定，是因为占位在**任何 await 之前**就完成了 ——
  它不依赖调度，只依赖那把幂等键。
- **出站对端是测试替身**：`tests/support/fake-his-server.ts` 里的真实 HTTP 服务
  （生产客户端与替身走同一条 `fetch` 代码路径），它额外逐条记账以统计重复计费。
  它是**测试数据层**，不是产品的最终对接方式；真实对接形态见 `docs/api/his-charging.md`。
- **计费发生在关台回写**，不在入站那一刻：三个场景都走同一条
  `writeBackOperationCharges` 路径，所以「对端收到几条明细」直接等于
  「台账里落了几行」—— 这正是本对比要看的量。
- **台账跑在内存 SQLite**（`:memory:`）：压测量的是幂等与判定逻辑，不是磁盘吞吐；
  磁盘上的持久化行为由 `node --test dist/tests/db-migrations.test.js` 一类用例覆盖。
- **单机单进程**：并发来自 200 个同时在途的 HTTP 请求
  （真实 socket、真实请求头与请求体），不是多进程压测；跨进程去重靠台账里的
  唯一索引与租约，语义见 `docs/api/errors.md`。
- **耗时两列不可直接相比**：朴素基线少走验签、码制归一与占位三层，所以更快；
  **本对比的看点是重复计费条数，不是耗时**。
- **朴素基线不是产品代码**：它是 `scripts/lib/concurrency-harness.ts` 里的一段参照实现，
  用来说明「少了幂等层会发生什么」；它不参与产品运行路径。
